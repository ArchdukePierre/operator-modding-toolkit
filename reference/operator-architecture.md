# OPERATOR, Architecture Reference

## 1. Executive read

OPERATOR is a Unity 6000.3.8f1 / HDRP / IL2CPP tactical shooter built by a very small team around one prolific developer (`milk_drinker`, whose name is the source-path root for the newest code). Assembly-CSharp carries ~785 namespace-less `Il2Cpp.*` types plus a further ~160 vendor assemblies. It is not a prototype: the hot paths are engineered by someone who has clearly profiled them. It is also not a clean codebase: it is a five-year accretion in which almost nothing was ever deleted.

Note on evidence quality: method bodies **are** readable. Game code in `GameAssembly.dll` lives in a PE section literally named `il2cpp` (RVA `0x6F2000`, size `0x4860081`), not `.text`, and a 165,503-entry RVA→`Assembly!Type::Method` map exists. Where this reference cites an RVA, the claim came out of disassembly, not signature inference. Where it says "likely" or "needs-runtime", it did not.

**The rewrite pattern.** A sweep for types whose only members are `.ctor`/`.cctor` returns **53 empty husks**. `FirstPersonController`, `Stance`, `PlayerCanvas`, `Door`, `DoorHandle`, `Helicopter`, `Flashlight`, `LobbyController`, `BulletPooled`, `BulletFlyBy`, `Mirror_TeamDeathmatch`, `VoiceChatEnabler`, `SpawnNetworkedObject`, `InteriorCollider`. Each is the gutted predecessor of a live V2/V3: `DoorV2`, `HelicopterV3`, `GrenadeV2`, `WeaponV3`, `MasterController`+`Il2CppCMF.AdvancedWalkerController`, `BulletManager`/`BulletInstance`, `MenuControllerV2`, `OccludeSource`+`AudioOcclusionJobManager`, `WeaponSFX`, `Cerebus*`. Beyond the fully-empty set sit dozens of half-dead twins that still compile and still weave: `CERBERUS_OPBOARD` vs `CerebusOpboard`, `MenuController` vs `MenuControllerV2`, `WeaponSFXCompoment` vs `WeaponSFX`, `AudioOcclusion` (V1) vs `OccludeSource` (V2) vs `Il2CppAxelF.Occlusion` (V3, unwired), `Il2Cpp.TeamID` vs `TeamIdentifier`, `Il2Cpp.Grenade` vs `GrenadeV2`. **Version suffixes are not a reliability signal**: `BrainAIV2` is a two-method NavMeshAgent prototype that never runs, while the shipping brain is plain `Il2Cpp.BrainAI` (~95 methods, ~240 fields). Any mod that targets "the newest-sounding class" will bind to a corpse.

**Bought-in middleware does most of the load-bearing work.** Netcode is Mirror over FizzySteamworks; movement replication is Smooth Sync; locomotion is Character Movement Fundamentals; navigation is A* Pathfinding Project 5.x's **ECS** `FollowerEntity` (Unity NavMesh is inert, despite a vestigial `NavMeshAgent` field on `MasterController`); IK is FinalIK throughout; ragdolls are FIMSpace Ragdoll Animator 2; recoil, sway and springs are KINEMATION FPS Animation Framework; terrain is InTerra (not MicroSplat); AO is HTraceAO with GTAO/SSAO/hardware RTAO backends; upscaling is TND's 15-backend framework; foliage and props draw through a custom `BatchRendererGroup` renderer with GPU HZB culling; glass fracture is Oskar Sigvardsson's Voronoi library; saves are Easy Save 3; UI is five Michsky packs; the dev console is QFSW Quantum Console. Shipped-but-dead: RayFire (20 components, no `RayfireMan`), Dissonance, AmplifyImpostors, PPv2, Edgegap's whole relay+lobby stack, Mirror's `NetworkRoomManager`, and Unity's Book-of-the-Dead AxelF audio framework, which is more capable than the audio system the game actually uses. Asset-store *demo* scripts shipped verbatim into Assembly-CSharp (`FPSFireManager`, `FPS_RigidbodyFirstPersonController`, `PlayerMovement`, `WeaponSound`, the entire HDRP Water Samples suite) and pollute every name search.

**Trust posture: client-authoritative, thoroughly.** This is the single most important architectural fact. `WeaponV3.UserCode_CMD_SendBullet__Vector3__Quaternion__Vector3` and `WeaponV3.RPC_SendBullet` share RVA `0xA4FDC0`, the linker folded them because the server's handler body is nothing but a verbatim rebroadcast. Zero comparisons, no muzzle-plausibility check, no spread recompute. The MOA vector is rolled by `Random.Range` inside `DischargeRound` (`0xA447C0`) on the shooter's machine. Damage resolution is gated by one byte: `BulletInstance.isOwner` at `+0xC0`, tested at `0xAF2F4F`, the shooter's client decides which `Health` was hit, which limb, whether armour stopped it, and the final integer. `Health.CMDTakeDamage` is `[Command(requiresAuthority = false)]` (proven: the authority byte at `[rsp+0x28]` into `SendCommandInternal` comes from a zeroed register), as are `CMD_Bleed`, `CMD_Fracture`, `CMD_HitReaction`, `CMDProcessAIAnimation` and `Gore.CMD_SpawnGore`. Movement is Smooth Sync owner→server→non-owners with no validation anywhere in the type graph. `PlayerMaster.SetMyName(string, CSteamID)` is a Command, the scoreboard identity is client-claimed. `CMD_SetTeam(int)` is unrange-checked and `TeamManager.EnsureTeam(int)` will conjure the team. Appearance is an opaque client JSON blob (`CharacterModSync.CMD_SetCharacter`). Saves are unencrypted ES3 JSON on disk. There is no VAC/EAC integration; the only access control is `SteamAuthID`, a client-side HTTP allowlist fetch. The only server-authoritative subsystems are exfiltration (`GameManagerNetwork.ServerTickExtraction`), moderation (`SERVER_KickPlayer`/`SERVER_BanPlayer`, real `[Server]` methods with no weave), AI behaviour, and voice-line index selection.

**Where it is solid.** The performance architecture is strong. `GameManager` is the master pump and runs at least **nine independent round-robin schedulers** over global registries (AI logic, AI physics, bot health, weapon collision, weapon animation, AI aim correction, audio occluders, weapon mods, dynamic lights), and a dozen components have had their Unity lifecycle methods removed in favour of an externally-driven `CallUpdate()` convention. Ballistics, audio occlusion, AI LOS and cover generation all use batched `RaycastCommand` jobs with explicit frame budgets. `ObjectPooler` has bounded LRU reclaim with O(1) `LinkedListNode` removal and a "park" mode that teleports idle instances instead of `SetActive(false)`. `Destructible` replays late-join state with `skipForces=true` so a joiner sees settled debris. `MilkTransformSync` implements real request/grant ownership arbitration with a delayed-revoke grace window. The HDRP custom-pass stack, eleven-plus passes including a compute-shader NVG auto-gate with per-zone luminance reduction and persistent tube burn-in, is far beyond what the genre normally ships.

**Where it is tape.** Mirror spawn/scene races are a live, ongoing problem, and the code says so out loud: `GameManagerNetwork.DestroyObjectFailsafeCheckBecauseMirrorIsFuckingGayAsFuck(uint, NetworkConnectionToClient)`, `OhShitHomieYouGotFuckedBecauseMirrorIsDogShit(NetworkConnectionToClient, uint)`, `OnSceneLoadedMirrorHookFuckMirrorIHateMirror()`, `SpawnObjectsFailSafe()`, `LoadingFailsafe()`, `TestAllGayUnspawnedObjects()`. State is duplicated in at least six places: two extraction implementations (`ExfilZone` and `GameManagerNetwork` both own `canExtract`/occupant counts), two day/night authorities (`VectorTimeOfDay` drives it, `SunSettings` replicates it), two stance/lean replication channels, two casing-impact audio systems on mismatched material taxonomies, two FFA spawn pickers, three occlusion systems. Settings keys are cache-busted rather than migrated (`maxfps19823839183jnSliderValue`, `CurrentUpscalerNew` *and* `CurrentUpscaler_2026` with contradictory values). AI volume and voice-chat volume have sliders and setters but no persistence key. And a set of shipped typos is now permanently part of the wire format and the reflection surface: `CMD_Play_Folely_F_All`, `PvpGameode`, `Cerebus` (one R), `CalulateRating`, `SetNotifcationString`, `WeaponSFXCompoment`, `Richochet`, `TerrainLit ... or Heigher`, `NEW_ACHIEVEMENT_Tier1Gerogia`. Spell them wrong or your patch never binds.

## 2. Subsystem map

### 2.1 player-avatar

The avatar is not one component. It is three hubs plus a second networked GameObject.

`Il2Cpp.PlayerNetworking` is identity, weapons, IK and interaction, ~37 sibling components cache a reference to it, and `GameManager.myPlayerNetworking` hands you the local one with no scene search. `Il2Cpp.MasterController` is the physiology and camera layer: it owns `vaultSystem`, `playerStance`, `playerLean`, `characterAudio`, `characterNetworking`, `walkerController` (`Il2CppCMF.AdvancedWalkerController`), `mover`, `cameraController`. `Il2Cpp.Health` is damage, death and ragdoll, and it serves bots too (`isBot`, `brainAI`, `ProcessAIDamage`).

The structural surprise is that client authority is modelled as a **second networked object per player**: `PlayerNetworkingClientSide` and `PlayerMasterClientSide`, each with a `ServerSide` back-reference. Remote stance, lean, IK targets and the `SyncList<MagazineSyncInfo> MagsList` live there, not on `PlayerNetworking`. `PlayerStance`, `PlayerLean`, `CharacterNetworking` and `CharacterAudio` are data-only classes with zero methods; all their logic is inside `MasterController`.

Damage is seven limbs (`HealthBodyPart` = Head, Chest, Stomach, LArm, RArm, LLeg, RLeg, plus `SERVER` and `NONE`), each with its own HP SyncVar and its own `BleedingDamage_*` rate SyncVar; fractures exist only for the four limbs. `TotalHP` is not an independent pool, it is recomputed as the sum of the seven (`0xF1779B`-`0xF177D9`). Death thresholds, read from the jump table in `UserCode_TakeDamage`: `HeadHP <= 1.0` (an intentional one-point margin), `ChestHP <= 0`, or `TotalHP <= 0`. Stomach and limbs can never kill directly. `shooterID == -3` is a reserved sentinel for "no attributable shooter" and is what the bleed tick passes. `MedicalSystem` is almost entirely client-local: one SyncVar (`currentMorphineInUse`), one Command, and every tourniquet flag, pain value and heart rate purely local.

**The one thing:** `Health` has no `Update`. It is externally ticked by `GameManager` through `Health.CallUpdate()` (`0xF09210`, xref-confirmed as the only caller) and distance-culled via `CullDistance`/`cullBehaviour`. Patching `Health.Update` does nothing. This "CallX" convention is repo-wide, `WeaponCollision.CallUpdate`, `WeaponMod.CallLateUpdate`, `DynamicLight.CallUpdate`, `BotAimCorrection.CallLateUpdate`, `FootstepAudioController.CallUpdate`, `AgentController.CallUpdate`, `WeaponSFX.CallFixedUpdate` all follow it.

### 2.2 weapons-ballistics

Fully simulated projectiles, no hitscan. `Il2Cpp.BulletManager` (singleton) ticks in `FixedUpdate` (`0xAF6C40`): snapshot the live list, `BulletInstance.BeginManagedTick` fills a `NativeArray<RaycastCommand>`, `RaycastCommand.ScheduleBatch` + `JobHandle.Complete`, then `BulletInstance.Travel` per bullet. Correcting a common misreading: **`Travel` (`0xAF5DF0`) calls `UnityEngine.Physics.Raycast` directly at `0xAF6206`**. The batched job is a coarse chord broad-phase; the actual hit is found by a conventional per-substep raycast (`predictionStepsPerFrame` = 6 on the generic round). `Il2Cpp.Bullet` is an inert MonoBehaviour stat template; `BulletInstance` is the pooled sim object with no Transform and no Unity lifecycle, duplicating ~40 fields.

Fire chain: `WeaponV3.Update` (`0xA54B60`) polls `InputLayer.GetKey(InputKey.Shoot)`, fire modes are separate code paths behind a jump table, and only the full-auto branch (`0xA565F2`) passes `ActivatedThisFrame=false`. `CanFire()` (`0xA42CF0`) checks weapon *completeness* (`WeaponMods.CheckIfWeaponIsComplete`), not ammo or rate; rate lives in the `fireTimer` field. `Fire()` → `DischargeRound()` → `BulletShell.FireRound(hasAuthority)` (the misfire roll; failure sends `CMD_malfunctionMisfire`, hash `0x331FA040`) → `SpawnBullet()`. `WeaponV3.CMD_Fire`/`RPC_Fire` is a **cosmetic** channel carrying one bool; `CMD_SendBullet`/`RPC_SendBullet` carries the ballistics.

`GunStats` and `GunFunction` are pure data containers with zero behaviour methods, and `GunStats` has **no damage field**. Lethality belongs entirely to the loaded round (`Bullet.damage`, an `int`). Penetration is `SurfaceInformation` (ScriptableObject) vs `penetrationAmount`/`armourPenetration`; armour is a nine-tier NIJ table on `Il2Cpp.Armour`. `BulletInstance.GetPenChance(float)` receives the **plate's durability fraction**, not the victim's health (`0xAF25D1`ff). A stopped round converts to blunt trauma using the *armour's* multiplier and simultaneously loses all bleed and fragmentation. Arm hits use `armDamageMultipiler` (1.8 stock) as a *replacement*, so they do more damage than torso hits. Attachments replicate as one JSON string SyncVar, `WeaponMods.JSON_MOD_STRING`, whose hook rebuilds the whole weapon; the wire schema is `Network_WeaponPreset` where `ModParents[i].aID` is an **ordinal index into `ModIDs`**, not a mod id.

**The one thing:** `WeaponV3.CMD_SendBullet` is the highest-value seam in the game and simultaneously its plainest cheat vector. Prefix it to rewrite spread and origin; hook `UserCode_RPC_SendBullet` to observe every shot from every player. Any server-side anti-cheat must re-derive spread inside `UserCode_CMD_SendBullet`, because today that method contains no arithmetic at all.

### 2.3 ai-brain

`Il2Cpp.BrainAI` is the brain. Navigation is `AgentController.Agent` → `Il2CppPathfinding.FollowerEntity` (A* 5.x ECS), this is the *only* place Assembly-CSharp touches A* at all, and no game code ever calls `AstarPath.Scan`/`UpdateGraphs`, so a spawned bot attaches to the graph passively by enabling its component. Seeker/RichAI/AIPath tutorials do not apply.

The FSM has exactly six states: `BrainAI/States` = {Idle, TargetSighted, WasSighted, FallBack, Suppress, Evade}. Attack, Chase, CautiousAdvance, Patrol and Wander are *methods* called from within states. `SetNewAiState(States)` is the single transition funnel. Perception is `EyesAI` with three passes (`Vision`, `DoorVision`, `Hearing`), stance-aware eye heights, per-posture visibility gates (`CanSeeIfProne` can be false), and **scored** target selection via `EyesAI.ScoreTarget`, not nearest-first. Memory is four independent position channels with independent timestamps (`LastKnownTargetPosition`, `LastHeardTargetPosition`, `LastCommsTargetPosition`, `LastSuppressTargetPosition`), a real sensor-fusion model. Radio comms stage a *delayed* response (`_pendingCommsResponse` → `ProcessPendingComms` → `ExecuteBackupResponse`) rolled between `CommsDelayMin`/`Max`.

Cover is generated at runtime by `DynamicCoverFinder` (job-batched, hard `maxQueriesPerFrame` budget, pooled points, and an anti-clumping reservation list with `MinCoverSeparation`), no baked cover volumes, so custom maps need none. The AI **does not roll to hit**: `GenerateNearMissOffset` and `GetDifficultyKillShotOffset` displace the aimpoint and `WeaponsAI.SERVER_SendBullet` fires real projectiles. Doors are A* traversal tags (`doorWalkLayer`/`doorOpenLayer`/`doorBreachLayer`) flipped by `SetDoorMode`; breaching runs through `BotOffmeshLinkHandler`, which implements `IOffMeshLinkStateMachine` and keeps `Dictionary<DoorV2,float> _doorCooldowns`. Spawning is `RaidManager`, not `BotSpawner` (dead), and `RaidManager.SERVERONLY_CustomAISpawnList_AddAI(string)` + `RespawnCustomAI()` against `GameManager.allAITypes_s` is a shipped, string-keyed custom-enemy API.

**The one thing:** **no AI decision ever crosses the wire.** `BrainAI`'s only weaved RPCs are the suicide-bomber pair. `NetworkAnimatorSyncNPC` replicates presentation only, speeds, aim target, crouch/prone/combat bools, and clients re-run `AiAnimationController`/`AiRotationController`/`BotAimCorrection` locally. A client-side mod cannot read a bot's state, target or cover. Every AI mod must run on the host.

### 2.4 netcode-session

`Il2Cpp.NetworkManagerVectorGames` (Mirror `NetworkManager` subclass, static `instance`) owns the session; `Il2CppVectorGames.SteamLobby` owns matchmaking. Two transports are wired, `Steam` (FizzySteamworks, almost certainly next-gen `SteamNetworkingSockets` given the ping-location API in `EstimateLobbyPing`) and `OfflineTransport`, plus a public `startClientKCP()` and Mirror's stock `NetworkManagerHUD` shipped in retail. Four more transports and the entire Edgegap stack compile in unused.

The server browser works around Steam's 50-result cap with **time-bucketed lobby keys** (`UseTimeBucketedKeys`, `LobbyKeyBucketMinutes`, `BuildBucketKey`, `IncludeLegacyKeyInSearch`) and a shipped tooltip stating the value "MUST match across all host & client builds", change it and you partition yourself out of the vanilla list.

Replication idioms, in order of how much you should trust them: `Smooth.SmoothSyncMirror` for player transforms (owner→server→non-owners, relay not authority); `MilkTransformSync` for interactables (real `CMD_RequestOwnership` → `TargetRPC_GrantOwnership` handshake, per-recipient `TargetRpc` fan-out gated by `NetworkLOD.ShouldUpdate(Vector3, int stableId)`, pass distinct `stableId`s or everything ticks on the same frame); `MilkRigidbodySync` adds `releaseOwnershipDelay` + `TryCancelPendingRevoke()` so thrown props don't snap. Voice is MetaVoiceChat/Opus over `MirrorNetProvider.CmdRelayFrame` → `RpcReceiveFrame`, an **unfiltered ClientRpc**, so every client receives every speaker and proximity/radio filtering is cosmetic and local.

**The one thing:** naming does not track weaving. `SERVER_`-prefixed methods are sometimes real client Commands (`GameManagerNetwork.SERVER_RespawnALL`, `SERVER_RemoveKitForAllPlayers` both have `UserCode_`/`InvokeUserCode_` pairs) and sometimes plain `[Server]` methods (`SERVER_FailOperation`, `playerBoardItem.SERVER_KickPlayer`). Likewise `BotSpawner.CMDSpawnTargets` is not a Command at all. **The presence of `UserCode_X` is the only reliable test for whether an `X` named `CMD_`/`RPC_` crosses the wire.**

### 2.5 gamemodes-objectives

Two things are named GameMode. `Il2Cpp.GameMode` is the abstract NetworkBehaviour base; the enum is the *nested* `Il2Cpp.OperationsManager/GameMode` = {StandardPVE, StandardPVP, FFAPVP, PVE_HVTKILL, PVE_FINDINTEL, PVE_WAVESURVIVAL, PVE_ASSETDESTROY}. Seven modes, **four** controllers: `InfiltrationManager` serves all four PVE variants (the objective difference is `RaidManager` data, not a class), `PvpGameode` serves StandardPVP, `FFA` serves FFAPVP, `WaveSurvival` serves PVE_WAVESURVIVAL. `GameMode.singleton` identifies the live one.

`RaidManager` is **not** a mode, it is the per-map PVE content director sitting beside `InfiltrationManager`: AI pools, HVTs, reinforcements, IEDs, static vehicle AI, objectives (`ObjectiveSetter[]` for per-raid randomisation), per-map weapon bans (`prohibitedWeapons`/`mapSpecificWeapons`), and the exfil zone list. Win/lose lives on neither, `GameManagerNetwork.CompleteOperation()` and `SERVER_FailOperation()` are the single choke point for all four PVE modes, and they also own the mission-complete screen, the survival end screen, achievement checks, and a *second* extraction implementation duplicating `ExfilZone`'s.

`WaveSurvival` is the most complete mode and has the best content surface: `GetWave(int)` normalises two parallel wave sources (inline `SurvivalWave` structs and `SurvivalWaveObject` ScriptableObjects, selected by `useScriptableObjectWaves`), so waves can be appended at runtime. `PvpGameode` is a full round-based search-and-destroy with freeze time and a `Tie` state, but its `Team1SpawnPoints`/`Team2SpawnPoints` are scene-wired lists, which is the hard blocker on making arbitrary maps PvP-playable. `Mirror_TeamDeathmatch` is completely empty; `Il2Cpp.PVP` has only `Start`/`Update`.

**The one thing:** the mission-board tuning never reaches the server. `CMD_StartOperation(string, int, string, string, string, float)` carries scene, prep time, display name, infil time, achievement name and target time, **no game mode, no AI count, no difficulty, no PVP/FFA limits**. `OperationsManager.CurrentGameMode` is a SyncVar so only the server's value counts, and `FFA_KillLimit`/`PVP_RoundLimit` are plain fields with no `Network*` accessor. Static per-opboard config is identical on every client because it comes from the same prefab; runtime slider changes made by a non-host client have no synced channel. `OperationsManager.DebugStartOperation(string, string, GameMode)` is the only API that takes a mode explicitly and is the practical way to launch any of the 7 modes on any of the 31 scenes.

### 2.6 world-interaction

Two interaction generations coexist. Legacy is bespoke `StartInteraction(PlayerNetworking)` on `BreakerSwitch`, `InteractableChair`, `FullBodyInteraction`. Modern is `Il2Cpp.InteractableComponent` with `AccessInteractable`/`Interacted` and two prompt strings, a plain MonoBehaviour with no Mirror members, so each subclass does its own networking. Exactly four types derive from it (`AmmoReloader`, `ProjectorToggler`, `MilkRigidbodyRequestOwnership`, `ObjectiveInteractable`) and **nothing anywhere holds an `InteractableComponent` field**, so `PlayerNetworking.ProcessInteractable()` must be resolving it by `GetComponent` on the ray hit. Discovery is raycast-first (`ScanForInteractable`) with a proximity fallback (`ScanForNearbyInteractable`).

Destruction is content, not simulation: `Destructible` swaps five authored prefabs across three sections driven by a byte bitmask SyncVar, with the late-join replay path noted above. Nothing in the codebase references it, which is either an unwired feature or a `GetComponent`-only relationship. The only *real* runtime fracture is glass, `Il2CppGK.BreakableSurface` computes an actual Voronoi diagram at the impact point and builds shard meshes at runtime, and it has **no Mirror members at all**, so shard geometry differs per client by design and `SetDifficulty()` means low-spec clients get different shard counts.

Explosives are individually implemented and individually good: `SlapChargeExplosive` is a directional cone charge that senses whether it is stuck to a `DoorV2`, glass or a wall; `GrenadeExplosive` spawns real `SimulatedShrapnel` (velocity integration + raycast sweep, feeding the same `SurfaceInformation` path bullets use, so cover works against frags) and has separate `CheckPlayerConcussion`/`CheckAIConcussion` paths plus `ResolveSafeOrigin` to fix the flashbang-against-a-wall bug; `Missile` uses closest-approach detonation with a hard `_maxLifetime` and replicates its SFX variant by index. `Il2Cpp.Landmine.CMD_Explode(Health victim)` takes the victim's Health straight from a client and is the most suspicious trust boundary in this area.

**The one thing:** `Il2Cpp.ObjectPooler.instance.InstantiatePooled(prefab, pos, rot)` is the sanctioned spawn path, and you must **never** `UnityEngine.Object.Destroy` anything carrying a `PooledObject`, that trips the `PooledObjectDestroyedUhOh` recovery path. Also: `PoolInitializer` divides one global decal/VFX budget across all registered surfaces, so adding a `SurfaceInformation` shrinks every other pool toward `MinDecalsPerPrefab` unless you raise `TotalDecalBudget`/`TotalVFXBudget` in step.

### 2.7 render-hdrp

Roughly 180 shipped shaders in twelve families, recovered from `globalgamemanagers.assets`. The dev's own uber-family is `MilkShaders/*` (`Lit-Template`, `UERemap`, triplanar/POM/layered variants). Rebinding imported assets: `HDRP/Lit` for props, `HDRP/Decal` for decals, `Shader Graphs/S_Glass` for glass, but never blind-swap onto a Shader Graph material, since SG shaders use their own property IDs.

Four things dominate the frame. (1) `Il2CppBRGInstancedRenderer.BRGRenderer` draws vegetation and props through `BatchRendererGroup` with its own GPU HZB occlusion culling. **These objects have no GameObject and no Renderer**, `FindObjectsOfType`, renderer raycasts and material swaps all miss them, and `NakedTerrainRenderer` sets `drawTreesAndFoliage = false` so trees may not even have colliders. (2) The custom-pass chain: `NVGAutogateCustomPass` (compute-shader per-zone scene-luminance reduction, persistent tube burn-in RT, per-lens meter circles projected from the static `NvgLensFollower` registry), `NVGGrainCustomPass` (grain masked to the tube via a rendered lens mask), `ScopeDOF` (masked weighted depth-aware blur; it overrides `AggregateCullingParameters`, so it costs culling time even at zero strength), `CapsuleShadows` (an entire undocumented compute-driven capsule contact-shadow system with a `CapsulesHandler` registry), `FoliageBendPass` (ping-pong RT grass trample with exponential decay, published as global shader properties). (3) `HTraceAO` owns ambient occlusion and **creates and overwrites HDRP's own `ScreenSpaceAmbientOcclusion` volume override** on every `UpdateSSAO`, set the `HTraceAOProfile`, not the Volume. (4) `TNDUpscaler` is a fully static facade over 15 backends including DLSS4, FSR4, XeSS2 and PSSR; `GetActiveUpscaler()` is distinct from `GetSelectedUpscaler()` because selection can fail with no error.

`Il2Cpp.CameraSettings` is the graphics god object, with a static `AllCameraSettings` registry and plain instance methods (`SetBloom`, `UpdateShadowsQuality`, `SetMaxLod`, `SetVegetationLodBias`), all Harmony-patchable, unlike il2cpp field accessors. Iterate it and skip `isScopeCamera` or you will break optics.

**The one thing:** lighting and shadows are amortised twice over and are **stale by design**. `LightOptimizeManager` walks a slice of `LightOptimize` per frame; `GameManager` separately round-robins `DynamicLight.CallUpdate`; and every `DynamicLightSetting` owns an `OnDemandShadowMapUpdate` with per-distance-band refresh wait tables. Enabling, disabling or moving a `Light` directly without forcing `UpdateShadowMap()` leaves a shadow that does not match the light for up to the configured wait, and `DynamicLight` fakes the off state with a *material swap*, so toggling the `Light` component alone leaves the bulb mesh glowing.

### 2.8 audio

Occlusion is a batched `RaycastCommand` job, `AudioOcclusionJobManager` schedules in `Update`, completes and smooths in `LateUpdate`, time-sliced by `framesToSpread`. **One ray per source**, so occlusion is binary per source with no portal or diffraction model; the smoothing is what hides the pop. Three occlusion implementations ship: this one (V2), the data-only V1 `AudioOcclusion` driven by `GameManager` round-robin, and the unwired `Il2CppAxelF.Occlusion` (high- *and* low-pass plus speed-of-sound delay).

Weapon audio also has two generations, live `WeaponSFX` (five source slots: ShotClose, ShotFar, Suppressed, SuppressedFar, Interior; cached `Action` delegates to avoid per-shot allocation) and legacy `WeaponSFXCompoment`. There are **no `AudioReverbZone`s anywhere**: "indoor sound" is a clip swap plus filter parameters, chosen by `inInterior`/`inInteriorOpen`/`somethingAbove` (an upward raycast). Occlusion works by *rerouting sources to a different `AudioMixerGroup`* and stashing `originalAudioMixer`, assign your own mixer group to a live occluded source and it will be reverted with no warning on the next state flip.

`Il2Cpp.SoundFunctionLibrary.Instance.PlayClipAtLocation(...)` is the clean way for a mod to play a positional sound; it inherits pooling, mixer routing, the occlusion flag, interior tails and cutoff. `Il2Cpp.Gunshot` is the pooled three-layer distance-banded report object, and it is *also* the `SphereCollider` that notifies AI of the shot, carrying `Shooter`, `ShooterBrain` and `ShooterTeam`. Disable it to silence distant gunfire and you also make yourself inaudible to the AI.

**The one thing:** `SurfaceManager.instance.DefaultSurfaceTypes[i]` is the single best global sound-replacement point in the game. Overwrite the clip arrays on those `SurfaceInformation` ScriptableObjects and every footstep, landing, bullet impact and casing sound changes at once, for players and AI, on every map, with zero desync risk (only a volume float crosses the wire for footsteps). Because they are shared-by-reference SOs, the mutation is process-wide, cache originals and restore on unload.

### 2.9 progression-save

`Il2Cpp.SaveManager` is a fully static, PlayerPrefs-shaped facade over Easy Save 3 with a six-value file router (`SaveFileType` = Other, GameProgression, PlayerSettings, AudioSettings, Controls, KeyBinds). Files land in `%LOCALAPPDATA%Low\VECTOR INTERACTIVE\OPERATOR\Saves\Save0\` as **unencrypted, human-readable ES3 JSON**, despite `ES3Crypto`/AES shipping in the build. No signing, no checksum.

The routing matters. `GameProgression.es3` holds only mission unlock codes; the untyped `SetInt`/`GetInt`/`SetString` family carries no `SaveFileType` and hard-routes everything else into `Other.es3`, achievements, per-map best times, lifetime kill counts, graphics settings, and the character preset. Writing progression via `SaveManager.SetInt()` puts it in the wrong file and the opboard will never see it; use `SaveSteamStorage<int>(key, 1, SaveFileType.GameProgression)`. Writes are cached in `_dirtyFiles` and only committed by `FlushDirtyFiles()`, which nothing appears to schedule, call it explicitly, and note that editing an `.es3` while the game runs is futile.

Weapon presets are loose per-preset `.txt` files under `WeaponPresets/Version2/<Family>/<Name>.txt`, with shipped defaults sitting unpacked (Unity `.meta` sidecars and all) in `OPERATOR_Data\DefaultWeaponPresets\2\`. Character presets, by contrast, get exactly **one unnamed slot**, two escaped JSON strings, `CharacterPreset` and `CharacterPresetMods`, in `Other.es3`. Achievements have no manager type at all: three inline methods on `GameManagerNetwork` (`CheckAchievements`, `CheckTier1Challenge`, `CheckTier1NightChallenge`) plus authored gates on `CerebusOpboard` (`AchievementName`, `achievement_aiDifficulty`, `achievement_min_ai_amount`). Multi-slot save machinery is fully implemented and has never been used, `SaveInfo.es3` does not exist on a heavily-played install.

**The one thing:** the entire anti-cheat gate is one patchable property. `OperationsManager.get_EffectiveHasCheated()` is a real method computed over the plain field `HasCheated`, the SyncVar `NetworkHasCheated` and `DevCheatBypass`, and the devs shipped the bypass as a console command, `dev-bypass-cheatcheck`. Patch the property, never the field (il2cpp field accessors are not Harmony-patchable). It is a SyncVar, so a client cannot clear it for the server; a modded host can.

### 2.10 ui-shell

First, the trap that costs an hour: the interop namespace is `Il2CppMichsky.*`, **not** `Il2Cpp.Michsky.*`. Il2CppInterop prefixes the root namespace rather than inserting a segment. Same for `Il2CppMirror.*`, `Il2CppTMPro.*`, `Il2CppQFSW.QC.*`. Also, `all_types.txt`-style indexes list only namespace-less `Il2Cpp.*` game types, so no vendor type appears there at all.

Five Michsky packs ship; three are wired. Main menu is `MenuControllerV2` in the **Shift** style; the in-game pause/settings menu is `PlayMenu` in **MUIP**; the mission laptop is **DreamOS**. The same conceptual control exists twice in different packs (resolution is a raw `TMP_Dropdown` in `MenuControllerV2` and an MUIP `CustomDropdown` in `PlayMenu`), and both are live. The whole "Dark, Complete Horror UI" pack has zero references from game code, as do DreamOS's browser/mail/music/notepad apps, a free, already-loadable app surface for a laptop mod.

`Il2Cpp.PlayMenu` (static `singleton`, ~150 methods) is the richest hook surface in the shell: every graphics/audio/gameplay setter is a plain void method, plus `OpenSubmenu(string)`, `AllSubMenus`, and centralised cursor state (`ToggleCursorLogic`/`EnableCursorLogic`) that any mod window must route through. Keybinds are `Il2Cpp.InputLayer` (~89-value `InputKey` enum including eight ATAK entries), `Il2Cpp.KeyboardManager` is a completely empty stub. `HintManager.singleton.SpawnPopup(string, Popup/PopupType, bool spamDelay, bool slient)` gives on-brand styled feedback with no prefab and no bundle; `OnScreenNotification.SetNotifcationString(string)` is the separate weapon-state HUD channel (note the misspelling).

**The one thing:** the mission laptop is a **shared planning screen, not per-player UI**. `Il2Cpp.MissionLaptopNetworkState` (singleton) carries 19 SyncVars, every laptop in the level shows the same page, selection, difficulty, prep time and infil mask (a 64-bit `ActiveInfilMask`, which caps a map at 64 infils). Mutating `MissionLaptopDisplayer` directly desyncs clients; go through the network-state setters and hook the `On*Changed(previous, current)` hooks for the receive side. And for widget construction generally: **clone an existing in-scene widget, never `AddComponent` a bare one**, this build's Michsky components carry no shared theming asset, so styling comes entirely from the separate `UIManagerX` applier components and serialized references that only a clone brings with it.

**Authority ledger.** The shooter's client decides essentially everything: trigger timing, `CanFire`, the misfire roll, the MOA vector, muzzle pose, projectile simulation, every raycast, surface and armour resolution, penetration, ricochet, *which* `Health` and *which* body part was hit, the bleed/fracture/gore rolls, and the final damage integer. What a client-side mod **cannot** see: the AI count, difficulty and PVP/FFA limits that were moved on a slider but never entered the launch payload, those live on the host's own copy of the opboard prefab and never replicate. Prefix naming is not evidence of anything here; confirm weaving by the `UserCode_X` + `InvokeUserCode_X` pair, and settle `requiresAuthority` at runtime by dumping `Mirror.RemoteCalls.RemoteProcedureCalls.remoteCallDelegates` and reading each invoker's `cmdRequiresAuthority`.

### 4.2 Methods whose names lie about the wire

Establishing whether something crosses the wire requires the `UserCode_`/`InvokeUserCode_` pair. Verified individually `[M]`:

### 4.3 Bugs and probable bugs

1. **`DynamicLight` has no way to turn on except a SyncVar.** `CMD_TurnOff` + `RPC_TurnOff` + `TurnOff` + `TurnOffLocal` all exist. `CMD_TurnOn` is not weaved, and **there is no `TurnOn()` or `TurnOnLocal()` method at all** `[M]`. If the material swap and shadow refresh happen in the `TurnOff`/RPC path rather than in an `isOn` hook, restoring power leaves the off-material and/or a stale shadow `[P]`.
2. **Glass never resets, probably.** `GameManager` has a named `ResetAllDoors()` and no `ResetAllBreakableSurfaces()`, despite owning `BreakableSurfaces: List<GK.BreakableSurface>` and each pane having `Reload()` `[S]`. Two-line mod fix if confirmed.
3. **Glass state can diverge across clients by construction.** `BreakableSurface` has no Mirror members; break state and shard geometry are decided locally with locally-seeded randomness, and `SetDifficulty()` scales shard count with quality settings `[S]`.
4. **`DynamicLight.onChance` randomises which lights are lit** with no visible server seeding, so light layout may differ per client `[S]/[P]`.
5. **AI volume and voice-chat volume have setters and sliders but no persistence key.** `PlayMenu.SetAIVolume` and `SetVoiceChatVolume` exist; of ~40 `Key_*` strings only `Key_MasterVolume` and `Key_MusicVolume` are audio `[S]`. They should reset every launch.
6. **`AmbienceManager` leaks its trigger refcount.** It is refcounted by `triggersEntered` via `setInterior()`/`setExterior()`; an `AmbienceDynamic` trigger destroyed or unloaded while the player is inside it pins the ambience to interior `[S]/[P]`.
7. **Two competing lowpass overrides on one shared filter.** `MainCameraSingleton.overrideLowpassForHeadsetEffect` and `overrideLowpassForUnderwater` both drive `lowPassFilter`, the classic setup for two effects clobbering each other `[S]/[P]`.
8. **Casing impact audio has two implementations keyed to different taxonomies.** `ShellSFXComponent` hardcodes twelve per-material lists including `acs_Acid`, `acs_Electrical` and `acs_Fabric`, **none of which are `SurfaceTypeEnum` values**, while missing `Carpet`, `Brick`, `Dirt`, `Default` and `Flesh`. Meanwhile `SurfaceInformation` already provides `PistolCasingImpact`/`RifleCasingImpact`/`ShotgunCasingImpact` and `GetShellImpact(ShellAudioType)` `[S]`. Replacing casing sounds via one path leaves the other unchanged.
9. **Both `CurrentUpscalerNew` (=0) and `CurrentUpscaler_2026` (=1) exist in `Other.es3` with contradictory values** `[D]`. The convention is to mint a new suffixed key rather than migrate, so stale keys accumulate and it is not obvious which is authoritative.
10. **A crash loses progression.** Writes are cached in `_dirtyFiles`; **no method on `SaveManager` schedules a flush**, and `IsAllNullBytes(byte[])` exists specifically to detect the all-zero `.es3` produced by a kill during write `[S]/[D]`.
11. **Weapon presets appear to have been dropped by migration.** `Save0Migrated\WeaponPresets\Version2\SPR\` holds `Delta.txt`, `MARSOC.txt`, `MASRIC.txt` and `MK46\` holds `Delta 2.txt`, `MARSOC.txt`, none present under `Saves\Save0` `[D]`. The user may simply have deleted them in-game `[P]`.
12. **Adding a `SurfaceInformation` shrinks every other pool.** `PoolInitializer` divides `TotalDecalBudget`/`TotalVFXBudget` across the counted prefabs, so a mod adding surfaces must raise the totals in step `[S]`.
13. **Raising `penetrationAmount` without raising `maxImpactPenetration`/`maxImpactNonPenetration` gives penetration**, no decal, no SFX past the cap `[M]`.
14. **`Bullet.bluntDamageMultiplier` (0.2 on the generic round) appears to be dead data.** `ProcessBullet` reads only `_bluntDamageMultiplier[+0x134]`, copied off the `Armour` component `[M]`. Verify before shipping a mod that tunes it `[P]`.
15. **Fracture is rolled for any body part**, but `Health` only stores `Fractured_LArm/RArm/LLeg/RLeg` SyncVars `[M]/[S]`, head/chest/stomach fracture rolls have nowhere to land.
16. **The heavy-bleed rate of 10.0/s is a hardcoded immediate in `ProcessBullet`**, not a field `[M]`. It can only be changed by patching that method.
17. **`playerBoardItem`'s score SyncVars are `ushort`**, kills/deaths/points saturate at 65535 `[S]`.
18. **`MissionLaptopNetworkState.ActiveInfilMask` is a `long`**, a hard cap of 64 infils per map `[S]`.
19. **Changing `LobbyKey` or `LobbyKeyBucketMinutes` partitions modded hosts out of the vanilla browser**, the shipped tooltip says it must match across all builds `[D]`.
20. **`RaidManager` reads and writes `spawnChancePerPoint`, and `BotSpawnDetails` authors `Vector2` ranges that `BrainAI` stores as scalars**, overriding `BrainAI` post-spawn destroys per-bot variety `[S]`.
21. **`GroupDistanceCuller` runs `Update()` on every instance with no manager amortisation**, unlike every other LOD system in the build `[S]`.
22. **Reticle settings key off the runtime clone name** (`"Trijicon RMR(Clone) reticle setting"`), so renaming or re-instantiating an optic prefab orphans the saved choice `[D]`.
23. **`Il2Cpp.PlayerDrawing.RPC_ReceiveInitialTexture`'s weaved body got no friendly name**, it appears as `Method_Protected_Void_NetworkConnectionToClient_Il2CppStructArray_1_Byte_PDM_0`, with its invoker as `Method_Protected_Static_Void_NetworkBehaviour_NetworkReader_NetworkConnectionToClient_PDM_0`. Hook it by the mangled name `[S]`.

### 4.5 Design surprises worth internalising

- **Arm hits do more damage than torso hits** (`armDamageMultipiler = 1.8`, and the arm branch *replaces* rather than scales the total) `[M]`.
- **A headshot kill is `HeadHP <= 1.0`, not 0**, an intentional one-point margin, so "survive one headshot" is a one-field change to `initHeadHP` `[M]`.
- **Stomach and all four limbs can never kill directly**, only Head, Chest and the TotalHP sum can `[M]`.
- **`TotalHP` is a derived sum**, so `initTotalHP` does nothing `[M]`.
- **Damage decays by angle (`× incidenceAngle / 270`), never by range.** `Bullet.damage` is range-independent by design `[M]`.
- **Players never gore.** `Gore.CheckForGore` has exactly one caller in the binary: `Health.ProcessAIDamage` `[M]`. All the plumbing works for any character with a `gorePoints` array; adding player dismemberment means adding the call in the player branch of `ProcessBullet`.
- **Going prone before impact is mechanically different**, not cosmetic, it removes the heavy-bleed roll entirely and collapses two legs into one damage number `[S]`.
- **Suppressing the SR25 raises its RPM by 18%** `[D]`.
- **A plate that stops a round removes bleeding entirely** and converts to blunt using the *armour's* multiplier `[M]`.
- **Impact FX have no ownership gate**, so `VehicleHealth.CMD_TakeDamage`, `BreakableSurface.Break` and `BulletHittable.OnHit` are invoked N times for N clients `[M]`.
- **Kill notifications always precede the authoritative score change**, `Die` is a ClientRpc, `ProcessDeathServer` is polled from `CallUpdate` one or more frames later `[M]`.
- **`shooterID == -3` is a reserved sentinel** distinguishing bleed-out and environmental death from gunfire `[M]`.
- **Cracks are geometric per substep, not event-based** `[M]`.
- **AI hearing and gunshot audio are the same pooled object**, silencing one silences the other `[S]`.
- **The player-visible interaction switchboard is one 5.5 KB method** dispatching 25+ distinct systems `[M]`.
- **Trees are not GameObjects** and cannot be raycast, `GetComponent`ed or destroyed `[S]`.
- **Only intent crosses the wire for AI**, clients see animator SyncVars and nothing else `[S]`.
- **The mission laptop is a shared planning screen**, not per-player UI, 19 SyncVars `[S]`.
- **Michsky widgets in this build carry no shared theming asset**, clone prefabs, never `AddComponent` `[S]`.
- **Emotes and death animations both travel as animator state-name strings** `[S]/[M]`.

## 6. OPEN QUESTIONS AND THE PROBES THAT SETTLE THEM

**Netcode / trust**

1. **Is `requiresAuthority` false on the weaved `SERVER_`-named calls, and which direction are they?** Read Mirror's own registry: `Mirror.RemoteCalls.RemoteProcedureCalls.remoteCallDelegates` maps the function hash to an `Invoker` carrying `cmdRequiresAuthority`. Dump it at runtime and cross-reference the hashes. Critical for `GameManagerNetwork.SERVER_RespawnALL` (a griefing vector if any client can force a full-team respawn) and `Landmine.CMD_Explode(Health)` (kill an arbitrary player from any range if authority is not required).
2. **Does `Landmine.CMD_Explode` honour a remote `Health`?** From a non-authoritative client, call it against another player's `Health` component and see whether the server acts. Contrast `DoorV2`, which validates behind `Server_CheckDoorDamageResults`.
3. **Is the voice return leg a broadcast ClientRpc?** Two clients far apart, one speaking; log `MirrorNetProvider.RpcReceiveFrame` arrivals on the distant client. If frames arrive regardless of distance, every client receives every speaker's audio and host upstream scales with players squared.
4. **Which voice stack is actually enabled on a spawned player?** Check whether the live player object has an enabled `SteamworksVoiceChat` (it has the complete transport and hangs off `PlayerMaster.voiceChat`) or only `PlayerVoice`→`MetaVc`. Also check for any enabled `DissonanceComms`.
5. **Do the `PlayerNetworkingClientSide` / `PlayerMasterClientSide` NetworkIdentities actually grant client authority?** Read `NetworkIdentity.connectionToClient` / `isOwned` on a live remote player's ClientSide object. The types declare no Commands, so if authority is not granted those SyncVars can only be server-written and the "client-authority" reading is wrong.
6. **Is mid-session join permitted?** Attempt a Steam join against a host already inside an operation scene and watch whether `OnServerAddPlayer` runs. If joins are allowed, any new networked mission state a mod adds must be a SyncVar, not a one-shot Rpc.
7. **Can `TryGetSteamId` read a client-asserted value?** On the host, compare `PlayerMaster.thisPlayerSteam64` against `TryGetSteamId(conn)` for the same connection across a session. `OnServerAddPlayer` stamps it from the transport `[M]` and `UserCode_SetMyName` is an empty stub `[M]`, so divergence should be impossible, confirm nothing else writes it.
8. **Does an unmodded client survive an unknown `characterJSON`?** Call `CharacterModSync.ApplyCurrentModPreset` with a garbage blob and watch for an exception vs a quiet fallback. The Command handler does no validation `[M]`, so failure handling is entirely in the apply path.
9. **Does `FizzySteamworks.UseNextGenSteamNetworking` read true?** One field read; settles Legacy vs Next and whether relay is on.

**Ballistics / damage**

10. **Is `GameManagerNetwork.FriendlyFire` enforced at all?** It is not consulted in `UserCode_CMDTakeDamage` `[M]`. Set it false, shoot a teammate, and log inside `Health.TakeDamage` (5-arg) and the 4-arg RPC to find where (or whether) it is checked.
11. **Is `Bullet.bluntDamageMultiplier` dead?** Set it to an extreme value on a `Bullet` prefab, shoot armour that stops the round, and compare damage against the same test with `Armour.bluntDamageMultplier` changed. `ProcessBullet` reads only the latter `[M]`.
12. **Confirm the drag model.** Postfix `BulletInstance.Travel` and log `speed` each tick. `dragAmount 985` against `speed 1030` is consistent with a quadratic-drag denominator (≈110 g at muzzle) but that is arithmetic, not evidence.
13. **What is the exact `fragmentationChance` scale?** Set `maxFragmentationMultiplier` to a nonzero value and count frag events over a large sample against the 0-100 hypothesis.
14. **Does the barrel-length fire-rate branch work?** Flip `changeFireRateWithBarrels = true` on a live `GunStats`, author the three rates, and time shots with each barrel class.
15. **Is `BulletBlocker` a layer or a tag?** Check the layer of a `BulletBlocker` GameObject against `BulletInstance.layerMask`. The class is an empty marker `[S]`.

**AI**

16. **Does `teamConfidence` drive `FallBack`?** Log `BrainAI.teamConfidence` across a squad while killing members one at a time, and log state transitions from inside `RunBrainTick` (**not** `SetNewAiState`, it is inlined `[M]`).
17. **Do `EyesAI.FindTarget`'s per-call `NativeArray` allocations matter?** Wrap `EyesAI.UpdateEyes` in a profiler sample with 30+ bots. The allocation is confirmed `[M]`; only its cost is open.
18. **Which of `noJogWeight`/`noSprintWeight` are hard cutoffs?** Write `MasterController.totalWeight` directly and watch `RunState`.
19. **Does `staminaDepletionCount` lengthen the lockout?** Log `currentStaminaDelay` across successive exhaustions. Currently a hypothesis from field names alone.
20. **Which of `_hashCrouching` / `_hashCrouch` is live?** Set each in isolation and watch the animator.

**Modes / progression**

21. **Are non-host board slider changes dropped?** As a joined client, move the AI-count / FFA-kill-limit sliders, start the op, then read `OperationsManager.singleton.FFA_KillLimit` on the host.
22. **Does the server validate `CMD_HVT_ConfirmKIA`?** Send a bogus name and netId as a non-host client and watch whether `RPC_HVT_ConfirmKIA` fires. Check whether the handler cross-references `OperationsManager.AI_HVTs`.
23. **Which extraction state is authoritative?** Stand in an exfil and watch `ExfilZone.canExtract`/`PlayersInExfil` against `GameManagerNetwork.canExtract`/`PlayersInAnyExfil`/`isExtracting`/`extractionStartTime`.
24. **Which opboards actually set `AffectGamemode`/`GameModeOverride`?** Walk `OperationsManager.singleton.ActiveOperations` and `SimulationOperations` once at scene load and print each `CerebusOpboard`'s two fields. That listing is the definitive board-reachability answer.
25. **Which of FFA's two spawn pickers is live?** Instrument `FFA.EvaluateSpawn` and `GameManager.BestFFASpawn` and count calls during a round.
26. **Does anything drive `AlarmSystem`?** `FindObjectsOfTypeAll<AlarmSystem>()` in a loaded raid and watch whether `syncedState` ever leaves `None` while tripping the AI. Signatures cannot rule out a `GetComponent<AlarmSystem>().SetState(...)` inside another body or a scene UnityEvent.
27. **Does `SERVER_LoadOperation` have a live caller?** It has zero direct callsites `[M]` and makes a virtual `ServerChangeScene` call. Instrument it and start an operation to find the delegate/lambda or console path.
28. **Is `SaveSteamStorage` touching Steam at all?** Hook it and log, then watch for `SteamUserStats.SetAchievement` / `SteamRemoteStorage.FileWrite` in the same window, or write a `NEW_ACHIEVEMENT_` key directly and watch for a Steam overlay toast.
29. **Did migration drop weapon presets, or did the user?** Hook `WeaponPresetMigration.MigrateOldTxtPresets`/`MigrateES3Presets`, point a clean profile at a seeded legacy tree with awkward names (spaces, unicode, and the actual empty-basename `.txt` that exists under `MP5\` and `Noveske\`), and diff input against output.
30. **Do `SetAIVolume` / `SetVoiceChatVolume` persist?** Set them, restart, re-read. No `Key_*` string exists for either `[S]`.

**World / render**

31. **Is `Destructible` used by any shipped map?** Count `Resources.FindObjectsOfTypeAll<Destructible>()` after an operation scene loads, and put a logging prefix on `CmdRequestExplosion`/`ApplyExplosionVisuals` while detonating a grenade beside a wall.
32. **Is RayFire inert?** Check `RayfireMan.inst != null` and count `Resources.FindObjectsOfTypeAll<RayfireRigid>()`. If both empty, the runtime is free real estate for true fracture.
33. **Does glass state diverge?** Two clients; one shoots a window; compare the other client's pane renderer and `Shards`. Also check whether panes reset between operations (there is no `ResetAllBreakableSurfaces()`).
34. **Do trees have colliders?** Raycast a trunk in an operation scene and inspect the hit collider; check `Terrain.activeTerrain.drawTreesAndFoliage` and `TerrainCollider` state. `NakedTerrainRenderer` sets the flag false `[S]`.
35. **Is `DynamicLight.onChance` seeded server-side?** Two clients in the same scene; compare which lights are lit.
36. **Does turning power back on restore the material and shadow?** Flip a breaker off then on with two clients connected; compare bulb emissive and cast shadows against a fresh join. `CMD_TurnOn` is not weaved and there is no `TurnOn()` method `[M]`.
37. **Which of `VectorTimeOfDay` and `SunSettings` is present per scene?** `FindObjectsOfTypeAll` for both at scene load. Only `SunSettings` replicates.
38. **What is `TerrainQualitySwitch.SetAllTerrainQuality(int)`'s int→quality mapping?** Call with 0/1/2 and read `Terrain.materialTemplate.shader.name`.

**Tooling reminders**

- Any "which method calls which" question is answerable in seconds: `python xref.py "Type::Method"` for callers, `calls.calls(rva, 'name')` for callees.
- `method_rva == 0x710100` means the method is empty. 2,517 methods share that address.
- Zero xref callsites means inlined or dead, check before choosing a Harmony target.
- All RVAs and field offsets in this document are build-specific. Re-derive after a game update by rebuilding `rvamap.tsv`.
- InteropInspector renders nested types with `/` (`Il2Cpp.OperationsManager/GameMode`, `Il2Cpp.MasterController/RunState`). Under Git Bash a regex argument beginning with `/` is mangled by MSYS path conversion and matches nothing, use `[/]` or run from PowerShell.
- The 943-name type index survives at `<scratchpad>\allnames.txt` / `alltypes.txt` / `full.txt`. A flattened copy of `teardown_findings.json` is at `<scratchpad>\findings_flat.txt` (and, having overwritten the prior Phase-1 index, also at `<scratchpad>\all.txt`).
